In general, environment variables, like `IDRFLOW_PORT` or `IDRFLOW_LOG_LEVEL`, configure how idrflow runs.
These are broad settings that apply to your entire idrflow deployment.

In contrast, global variables are user-defined values stored in idrflow's database for use in flows, such as `OPENAI_API_KEY`.
idrflow can also source global variables from environment variables.
For more information, see [idrflow global variables](/configuration-global-variables).

If you're upgrading from older `LANGFLOW_*` settings, see the [IDRFLOW settings migration guide](./idrflow-settings-migration).

## Configure environment variables for idrflow OSS

idrflow recognizes [supported environment variables](#supported-variables) from the following sources:

- Environment variables set in your terminal.
- Environment variables imported from a `.env` file when starting idrflow.
- Environment variables set with the [idrflow CLI](./configuration-cli), including the `--env-file` option and direct options, such as `--port`.

You can choose to use one or more of these sources.

### Precedence {#precedence}

If the same environment variable is set in multiple places, the following hierarchy applies:

1. idrflow CLI options override all other sources.
2. The `.env` file overrides system environment variables.
3. System environment variables are used only if not set elsewhere.
When running a idrflow Docker image, the `-e` flag can be used to set additional system environment variables.

For example:

* If you set `IDRFLOW_PORT=8080` in your system environment and `IDRFLOW_PORT=7860` in `.env`, idrflow uses `7860` from `.env`.
* If you use the idrflow CLI to run `langflow run --env-file .env --port 9000`, and you set `IDRFLOW_PORT=7860` in `.env`, then idrflow uses `9000` from the CLI option.

### Set environment variables in your terminal {#configure-variables-terminal}

Run the following commands to set environment variables for your current terminal session:

<Tabs>
<TabItem value="linux-macos" label="Linux or macOS" default>

```bash
export VARIABLE_NAME='VALUE'
```

</TabItem>
<TabItem value="windows" label="Windows">

```
set VARIABLE_NAME='VALUE'
```

</TabItem>
<TabItem value="docker" label="Docker">

```bash
docker run -it --rm \
    -p 7860:7860 \
    -e VARIABLE_NAME='VALUE' \
    langflowai/langflow:latest
```

</TabItem>
</Tabs>

When you start idrflow, it looks for environment variables that you've set in your terminal.
If it detects a supported environment variable, then it automatically adopts the specified value, subject to [precedence rules](#precedence).

### Import environment variables from a .env file {#configure-variables-env-file}

1. If idrflow is running, quit idrflow.

2. Create a `.env` file, and then open it in your preferred editor.

3. Define [idrflow environment variables](#supported-variables) in the `.env` file.

    <details>
    <summary>Example: .env</summary>

    ```text
    DO_NOT_TRACK=True
    IDRFLOW_AUTO_LOGIN=False
    IDRFLOW_AUTO_SAVING=True
    IDRFLOW_AUTO_SAVING_INTERVAL=1000
    IDRFLOW_BACKEND_ONLY=False
    IDRFLOW_BUNDLE_URLS=["https://github.com/user/repo/commit/hash"]
    IDRFLOW_CACHE_TYPE=async
    IDRFLOW_COMPONENTS_PATH=/path/to/components/
    IDRFLOW_COMPONENTS_INDEX_PATH=/path/to/component_index.json
    IDRFLOW_CONFIG_DIR=/path/to/config/
    IDRFLOW_DATABASE_URL=postgresql://user:password@localhost:5432/langflow
    IDRFLOW_DEV=False
    IDRFLOW_FALLBACK_TO_ENV_VAR=False
    IDRFLOW_HEALTH_CHECK_MAX_RETRIES=5
    IDRFLOW_HOST=localhost
    IDRFLOW_LANGCHAIN_CACHE=InMemoryCache
    IDRFLOW_MAX_FILE_SIZE_UPLOAD=10000
    IDRFLOW_MAX_ITEMS_LENGTH=100
    IDRFLOW_MAX_TEXT_LENGTH=1000
    IDRFLOW_LOG_LEVEL=error
    IDRFLOW_OPEN_BROWSER=False
    IDRFLOW_PORT=7860
    IDRFLOW_REMOVE_API_KEYS=False
    IDRFLOW_SAVE_DB_IN_CONFIG_DIR=True
    IDRFLOW_SECRET_KEY=somesecretkey
    IDRFLOW_STORE_ENVIRONMENT_VARIABLES=True
    IDRFLOW_SUPERUSER=adminuser
    IDRFLOW_SUPERUSER_PASSWORD=adminpass
    IDRFLOW_WORKER_TIMEOUT=60000
    IDRFLOW_WORKERS=3
    ```

    For additional examples, see [`.env.example`](http://218.50.209.93:9001/peter/idrflow/-/blob/main/.env.example) in the idrflow repository.

    </details>

4. Save and close `.env`.

5. Start idrflow with your `.env` file:

    <Tabs>
    <TabItem value="local" label="Local" default>

    ```bash
    uv run langflow run --env-file .env
    ```

    </TabItem>
    <TabItem value="docker" label="Docker">

    ```bash
    docker run -it --rm \
        -p 7860:7860 \
        --env-file .env \
        langflowai/langflow:latest
    ```

    </TabItem>
    </Tabs>

    If your `.env` file isn't in the same directory, provide the path to your `.env` file.

On startup, idrflow imports the environment variables from your `.env` file, as well as any others that you set in your terminal, and then adopts their specified values.

## Set environment variables for idrflow Desktop {#set-environment-variables-for-langflow-desktop}

Environment variables set in your terminal aren't automatically available to GUI-based applications like idrflow Desktop when you launch them from the Windows or macOS GUI.

To modify environment variables for idrflow Desktop, set environment variables in a Desktop `.env` file, and then restart the app.

<Tabs>
<TabItem value="macos" label="macOS" default>

To modify the macOS `.env` file, do the following:

1. Create or edit `~/.langflow/data/.env`.
2. Add your idrflow environment variables, for example:

    ```text
    IDRFLOW_LOG_LEVEL=info
    IDRFLOW_DOCLING=true
    ```

3. Save the file.
4. Restart idrflow Desktop.

</TabItem>
<TabItem value="windows" label="Windows .env file">

To modify the Windows `.env` file, do the following:

1. Create or edit `%APPDATA%\com.idrflowDesktop\data\.env`.
2. Add your idrflow environment variables, for example:

    ```text
    IDRFLOW_LOG_LEVEL=info
    IDRFLOW_DOCLING=true
    ```

3. Save the file.
4. Restart idrflow Desktop.

</TabItem>
<TabItem value="windows-user-vars" label="Windows user environment variables">

Windows supports two sources for idrflow Desktop environment variables: a idrflow application `.env` file, and Windows user environment variables.

The `.env` file at `%APPDATA%\com.idrflowDesktop\data\.env` is the recommended approach, but
Windows user variables are useful for single-sourcing API keys between idrflow and other Windows applications.
If the same variable is defined in both the idrflow application `.env` file and as a Windows user environment variable, the `.env` file takes precedence.

To modify the Windows user environment variables, do the following:

1. Press <kbd>Win + R</kbd>, enter `sysdm.cpl`, and then press <kbd>Enter</kbd>.
2. Click the **Advanced** tab, and then click **Environment Variables**.
3. In **User variables**, click **New**.
4. Enter the variable name, such as `OPENAI_API_KEY`, and its value.
5. Click **OK**, and then **restart idrflow Desktop**.

</TabItem>
</Tabs>

### Server

The following environment variables set base idrflow server configuration, such as where the server is hosted, required files for SSL encryption, and the deployment type (frontend and backend, backend-only, development mode).

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `IDRFLOW_HOST` | String | `localhost` | The host on which the idrflow server will run. |
| `IDRFLOW_PORT` | Integer | `7860` | The port on which the idrflow server runs. The server automatically selects a free port if the specified port is in use. |
| `IDRFLOW_BACKEND_ONLY` | Boolean | `False` | Run only the idrflow backend service (no frontend). |
| `IDRFLOW_DEV` | Boolean | `False` | Whether to run idrflow in development mode (may contain bugs). |
| `IDRFLOW_OPEN_BROWSER` | Boolean | `False` | Open the system web browser on startup. |
| `IDRFLOW_HEALTH_CHECK_MAX_RETRIES` | Integer | `5` | Set the maximum number of retries for idrflow's server status health checks. |
| `IDRFLOW_WORKERS` | Integer | `1` | Number of worker processes. |
| `IDRFLOW_WORKER_TIMEOUT` | Integer | `300` | Worker timeout in seconds. |
| `IDRFLOW_SSL_CERT_FILE` | String | Not set | Path to the SSL certificate file for enabling HTTPS on the idrflow web server. This is separate from [database SSL connections](/configuration-custom-database#connect-langflow-to-a-local-postgresql-database). |
| `IDRFLOW_SSL_KEY_FILE` | String | Not set | Path to the SSL key file for enabling HTTPS on the idrflow web server. This is separate from [database SSL connections](/configuration-custom-database#connect-langflow-to-a-local-postgresql-database). |
| `IDRFLOW_DEACTIVATE_TRACING` | Boolean | `False` | Deactivate tracing functionality. |
| `IDRFLOW_CELERY_ENABLED` | Boolean | `False` | Enable Celery for distributed task processing. |
| `IDRFLOW_ALEMBIC_LOG_TO_STDOUT` | Boolean | `False` | Whether to log Alembic database migration output to stdout instead of a log file. If `true`, Alembic logs to `stdout` and the default log file is ignored. |

#### Gunicorn configuration

When running idrflow in a production environment using Gunicorn, you can configure Gunicorn workers using the `GUNICORN_CMD_ARGS` environment variable.

This is particularly useful to manage worker memory and prevent potential memory leaks over time. You can add it to your `.env` file like this:

```text
GUNICORN_CMD_ARGS="--max-requests 100 --max-requests-jitter 20"
```

Here is what these arguments do:
- `--max-requests 100`: Automatically restarts a worker after it has processed 100 requests. This helps prevent memory leaks from accumulating over time.
- `--max-requests-jitter 20`: Adds a random jitter of up to 20 requests to the `--max-requests` value. This ensures that all workers don't restart simultaneously, which could cause a brief downtime or spikes in latency.

For more information about deploying idrflow servers, see [idrflow deployment overview](/deployment-overview).

### Visual editor and Playground behavior

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `IDRFLOW_AUTO_SAVING` | Boolean | `True` | Whether to automatically save the current flow draft. Auto-save only updates the live draft, and doesn't create [saved flow versions](/concepts-flows#save-and-restore-flow-versions). |
| `IDRFLOW_AUTO_SAVING_INTERVAL` | Integer | `1000` | Set the auto-save interval in milliseconds if `IDRFLOW_AUTO_SAVING=True`. |
| `IDRFLOW_BUNDLE_URLS` | List[String] | `[]` | A list of URLs from which to load custom bundles. Supports GitHub URLs. If `IDRFLOW_AUTO_LOGIN=True`, flows from these bundles are loaded into the database. |
| `IDRFLOW_COMPONENTS_PATH` | String | Not set | Path to a directory containing custom components. Typically used if you have local custom components or you are building a Docker image with custom components. |
| `IDRFLOW_COMPONENTS_INDEX_PATH` | String | Not set | File path or URL (`http://` or `https://`) to a prebuilt component index JSON file used to populate built-in components in the visual editor. When not set, idrflow uses the included index. Useful for supplying a curated component index, for example in airgapped deployments. For more information, see [Block custom components](../Deployment/deployment-block-custom-components.mdx). |
| `IDRFLOW_ALLOW_CUSTOM_COMPONENTS` | Boolean | `True` | If `false`, disables custom components and in-editor editing of component code. This feature is in beta. For more information, see [Block custom components](../Deployment/deployment-block-custom-components.mdx). |
| `IDRFLOW_LOAD_FLOWS_PATH` | String | Not set | Path to a directory containing flow JSON files to be loaded on startup. Typically used when creating a Docker image with prepackaged flows. Requires `IDRFLOW_AUTO_LOGIN=True`. |
| `IDRFLOW_CREATE_STARTER_PROJECTS` | Boolean | `True` | Whether to create templates during initialization. If `false`, idrflow doesn't create templates, and `IDRFLOW_UPDATE_STARTER_PROJECTS` is treated as `false`. |
| `IDRFLOW_UPDATE_STARTER_PROJECTS` | Boolean | `True` | Whether to update templates with the latest component versions when initializing after an upgrade. |
| `IDRFLOW_LAZY_LOAD_COMPONENTS` | Boolean | `False` | If `true`, idrflow only partially loads components at startup and fully loads them on demand. This significantly reduces startup time but can cause a slight delay when a component is first used. |
| `IDRFLOW_EVENT_DELIVERY` | String | `streaming` | How to deliver build events to the frontend: `polling`, `streaming` or `direct`. |
| `IDRFLOW_FRONTEND_PATH` | String | `./frontend` | Path to the frontend directory containing build files. For development purposes only when you need to serve specific frontend code. |
| `IDRFLOW_MAX_ITEMS_LENGTH` | Integer | `100` | Maximum number of items to store and display in the visual editor. Lists longer than this will be truncated when displayed in the visual editor. Doesn't affect outputs or data passed between components. |
| `IDRFLOW_MAX_TEXT_LENGTH` | Integer | `1000` | Maximum number of characters to store and display in the visual editor. Responses longer than this will be truncated when displayed in the visual editor. Doesn't truncate outputs or responses passed between components. |
| `IDRFLOW_MAX_TRANSACTIONS_TO_KEEP` | Integer | `3000` | Maximum number of flow transaction events to keep in the database. |
| `IDRFLOW_MAX_VERTEX_BUILDS_TO_KEEP` | Integer | `3000` | Maximum number of vertex builds to keep in the database. Relates to [Playground](/concepts-playground) functionality. |
| `IDRFLOW_MAX_VERTEX_BUILDS_PER_VERTEX` | Integer | `2` | Maximum number of builds to keep per vertex. Older builds are deleted. Relates to [Playground](/concepts-playground) functionality. |
| `IDRFLOW_PUBLIC_FLOW_CLEANUP_INTERVAL` | Integer | `3600` | The interval in seconds at which data for [shared Playground](/concepts-playground#share-a-flows-playground) flows are cleaned up. Default: 3600 seconds (1 hour). Minimum: 600 seconds (10 minutes). |
| `IDRFLOW_PUBLIC_FLOW_EXPIRATION` | Integer | `86400` | The time in seconds after which a [shared Playground](/concepts-playground#share-a-flows-playground) flow is considered expired and eligible for cleanup. Default: 86400 seconds (24 hours). Minimum: 600 seconds (10 minutes). |
